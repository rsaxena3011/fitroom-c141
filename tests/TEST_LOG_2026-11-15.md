## 5. Fixes applied during testing
- **webp rejected by the API.** The Clothsy API takes JPEG/PNG only.
  The server and `live-tryon.cjs` now upload the JPEG copies in
  `assets/*.jpg` (converted from the webp originals with PIL, quality 88);
  the browser still displays webp. Caught before any live call.
- **/api/status must not report dead on a slow balance check.** A key
  configured now means `live:true`; credits are best-effort with an 8 s
  per-attempt timeout and `null` on failure.
- **All server fetch calls carry a 15 s timeout** (`AbortSignal.timeout`)
  with a shopper-friendly timeout message, after the upstream stalls in §6.

## 6. Clothsy API reachability from this VM — INTERMITTENT (upstream/egress)
Observed 2026-11-15 evening, both curl and Node fetch:
- Unauthenticated probes are fast when the egress cooperates:
  `GET https://api.clothsyai.fabricvton.com/` -> 200 in ~1.0-1.3 s;
  `GET /api/v1/tryons/<uuid>` (no auth) -> 401 in ~0.8-1.3 s;
  `GET /api/v1` -> 404 in ~0.9 s.
- Authenticated calls repeatedly stalled at the TLS handshake (no
  ServerHello within 6-12 s), in several windows across the evening:
  `GET /api/v1/account` + Bearer key (curl and Node), `POST /api/v1/images`
  + Bearer key + multipart body (curl and Node). The same paths answered
  fast in other windows. The docs site (`clothsyai.fabricvton.com`) always
  answered fast (200 in ~1.2 s).
- Interpretation: the API backend is alive and behaves per the docs
  (401 without a key is exactly the documented `INVALID_API_KEY` path);
  authenticated calls stall intermittently through this VM's egress proxy.
  It may also be specific to invalid keys (slow key lookup). This is NOT
  proven as an API outage, and it is not a code defect: the same requests
  succeed in good windows. The real-key run (`scripts/live-tryon.cjs`)
  is the follow-up that settles it — retry from the VM, and if the stall
  persists, from a normal network. The server degrades gracefully either way.
